# Бриф «Интернет-магазин в приложении eFrumos» — разбор против текущего состояния efrumos

Дата: 2026-09-25. Источники: бриф `eFrumos_IT_brief eFrumos app.docx`
(версия от 23.08.2026), схема интеграционного слоя «Вариант 3», код
`efrumos` (сайт) и `eFrumos-backend` (бэкенд приложения лояльности),
ответы 1С от 21, 24 и 25.09 (`1c-open-items.md`).

## 1. Что в брифе

Приложение лояльности (`eFrumos-backend`: Laravel, вход по телефону + OTP,
Sanctum, бонусы через API 1С `srv-distr.solvex.md:8082`, вебхуки 1С
`transaction`/`balance-update`/`promotions` с Bearer-токеном и идемпотентностью
по `event_id`, Horizon, push, Filament) превращается в канал продаж: каталог,
корзина, оплата, push по заказу.

Принцип: сайт (efrumos) — единственный источник каталога, корзины и заказов;
бэкенд приложения — **тонкий клиент к сайту**. Заказ создаётся через общий с
сайтом интеграционный узел одновременно в 1С и Bitrix24, после оплаты статус
обновляется в обеих системах (схема «Вариант 3»).

Этапы: 1 аудит интеграций · 2 UX/UI · 3 единый вход · 4 каталог · 5 корзина,
заказы, 1С/Bitrix24 · 6 объединение профиля · 7 оплата картой (Moldindconbank)
· 8 push по заказу · 9 тесты и поэтапный запуск · 10 стабилизация.

## 2. Схема против реальности

| Блок схемы | Состояние в efrumos (25.09) |
|---|---|
| Интеграционный слой (Order Integration Service) | Есть: `OrderIntegrationService`, шлюз 1С, повторы (`SubmitOrderToIntegrationLayerJob`), таблица соответствий `integration_id_mappings`, проверка рассинхронизации |
| Проверка и резерв в 1С | Резерв — `CreateOrder`, работает. Остатки проверяются по кешу обмена каталога; живой `GetSKUArray` по GUID подтверждён (0,3–0,6 с), в проверку не подключён |
| Создание заказа в 1С | Есть: `CreateClientPoint` + `CreateOrder`. Ответ 1С получит доп. поле `AdditionalInfo` `{"orderSum","deliverySum","total"}` — обещано к концу дня 28.09 |
| Создание сделки в Bitrix24 | **Снято заказчиком 10–11.09, код удалён.** Менеджерам заказ уходит отдельно в Platon/Progression (`SendOrderToAmoCrm`), односторонний запрос при оформлении |
| Ответ сайту: номер, сумма, статус | Номер (`ObjectCode`) сохраняем; сумма от 1С — после 28.09; статус — через вебхук |
| Платёжная система, вебхук результата | Есть: VictoriaBank, серверный callback — единственный источник истины по оплате |
| Обновление в 1С после оплаты | Есть: `CreatePayment`, **только для оплаты картой** |
| Обновление в Bitrix24 после оплаты | Нет (Bitrix24 снят) |
| Статусы из 1С обратно в слой | Приёмник готов и проверен: `POST /webhooks/onec/order-status`, контракт 1С (`xml_id`, `status`, `token`…). Со стороны 1С не включён, токен на dev не прописан |
| Склад / доставка / уведомления клиенту | Внутри 1С; наружу — только статусы вебхуком |

## 3. Расхождения с брифом

1. **Bitrix24 больше нет.** Этап 5 и схему надо переписать: вместо Bitrix24 —
   Platon/Progression (система на Bitrix Site Manager, по терминологии 1С —
   amoCRM), причём канал односторонний, статусов оттуда нет.
2. **Банк — VictoriaBank**, не Moldindconbank (этап 7). В базе остались
   поля `maib_*` — историческое название, не банк.
3. **Наличные заказы в 1С не отправляются** (ответ 1С 24.09: в 1С должны
   попадать только оплаченные на сайте заказы; оплата при получении идёт в
   amoCRM). Реализовано 24.09 (`pay_method !== 'card'` → пропуск в
   `SubmitOrderToIntegrationLayerJob`). Для приложения: оформление с
   оплатой при получении — отдельный путь без статусов из 1С.
4. **Статусы приходят из 1С готовым списком `OrderStatuses`**, а не
   формируются нами. Соответствие push-уведомлениям (этап 8):
   - принят/оплачен — `НовыйОплачен`, `НовыйОжиданиеОплаты`, `Ожидание`;
   - собран — `Подтверждена`, `Расфасована`;
   - передан в доставку — `ВПути`;
   - доставлен — `Доставлен`, `СделкаЗавершена`;
   - отмена — `Аннулирована`; также `Оплачен`, `ЧастичноОплачен`,
     `ОжиданиеОплаты`.
   Даты статуса 1С не передаёт, **повторных попыток нет** — пропущенный
   вебхук = потерянный push. Статусы есть только у заказов, ушедших в 1С
   (карта).
5. **Сумму заказа определяет 1С** (товары + доставка). Приложение не должно
   считать доставку само. Сайт сейчас считает по фиксированному тарифу
   (50/100, бесплатно от 600) — по тексту сайта диапазон 50–80 / 80–100 лей;
   как 1С его считает, ответят 28.09. Для сторонней курьерской службы
   `deliverySum = null`: доставку клиент платит курьеру, онлайн списывается
   только `orderSum`.
6. **Прод заблокирован** 1С до утверждённой архитектуры. Описание потока 1С
   прислала 25.09, но заказчик его не утвердил.

## 4. Главный пробел: у сайта нет API для приложения

Проверено по коду:
- `routes/api.php` содержит только шаблонный `/user` (Sanctum);
- корзина хранится на cookie `basket` (`OrderController`), не привязана к
  пользователю;
- оформление заказа проходит reCAPTCHA v3 (`ajaxNewOrder`);
- все страницы и ajax-эндпоинты рассчитаны на браузерную сессию.

«Тонкий клиент к сайту» строить не на чем. В efrumos нужен **API приложения**
(отдельный префикс, авторизация сервис-к-сервису + идентификация пользователя):
- каталог: категории, фильтры, поиск, карточка товара, остатки, промо-цены;
- корзина на сервере, привязанная к пользователю;
- создание заказа без reCAPTCHA (с проверкой сервисного токена);
- начало оплаты (ссылка/данные для банка) и результат;
- список заказов и статус заказа.

И **обратный канал** efrumos → `eFrumos-backend` о смене статуса заказа — для
push (этап 8). Вебхук 1С приходит на сайт, потому что заказ создаёт сайт;
`eFrumos-backend` принимает такие события по своему образцу (Bearer-токен,
`event_id` для идемпотентности, очередь `webhooks`).

## 5. Открытые вопросы, которые бриф не закрывает

- **Бонусы при оформлении.** В `CreateOrder` нет поля для бонусов; бонусы
  живут в отдельном API лояльности. Вопрос 1 брифа остаётся главным: можно ли
  списывать бонусы в корзине и как это отражается в 1С. Есть только
  `PromoCode` в `CreateOrder`.
- **Два идентификатора клиента в 1С.** В приложении `client_id` (GUID
  лояльности), на сайте `ClientPointCode` (число торговой точки,
  `front_user.onec_client_point_code`). Их надо связать (этап 6); у гостя на
  сайте точка создаётся заново на каждый заказ.
- **Единый вход.** Пользователи сайта (email, соцсети) и приложения (телефон)
  не связаны; заказ на сайте привязывается к `front_user_id`.
- **История в личном кабинете** — одна лента или раздельно (вопрос 3 брифа);
  онлайн-заказы у приложения появятся только через API сайта.
- **Утверждение архитектуры** заказчиком, срок переноса на прод — за 1С.

## 6. Что делаем и в каком порядке (предложение)

1. Обновить бриф/схему: убрать Bitrix24, поправить банк, добавить путь
   «оплата при получении → только amoCRM», статусы из 1С.
2. 28.09: получить `AdditionalInfo` от 1С → сумма к оплате из ответа
   `CreateOrder`, ветка `deliverySum: null`.
3. Спроектировать API приложения на стороне efrumos (контракты, авторизация,
   привязка корзины к пользователю) до старта этапов 4–5.
4. Решить с заказчиком: бонусы в корзине, единый профиль, лента заказов.
5. Включить вебхук статусов у 1С (токен на dev, потом на проде), подключить
   push по соответствию из п. 3.4.
