### [BE] Аналитика «часто покупают вместе»

**Статус: ✅ Готово и живо проверено, исправлено под архитектуру из ТЗ**
_(перепроверено 2026-09-11: `recommendations:recalc-bought-together` реально
выполнилась при сегодняшнем деплое на dev — «Recalculated 10848 product
pairs from orders since 2025-09-11», без ошибок; команда и cron-расписание
на месте)_

Описание: построить расчёт связки «часто покупают вместе» на основе анализа
совместных заказов за последние 12 месяцев. Автоматический пересчёт — не реже
одного раза в сутки.

Изначально (в `feature/product-card`) `ProductRecommendations::coPurchased()`
считал связку **на лету при каждом открытии страницы товара** — прямой
SQL-join `orders`↔`basket`↔`basket` без кэша. При повторной сверке с `ТЗ.md`
(§3.2, 2026-09-04) нашлась прямая цитата документированного решения команды:
«периодический (**раз в сутки**, решение командное) **фоновый** расчёт пар
товаров в оплаченных заказах, результат **кешируется** в отдельную таблицу
типа `goods_frequently_bought_with`; **расчёт на лету при каждом открытии
страницы не делаем** (дорого по производительности...)» — код делал ровно то,
что ТЗ прямо просит не делать. Исправлено:

- Новая таблица `goods_frequently_bought_with` (миграция
  `2026_09_04_110000_create_goods_frequently_bought_with_table`).
- Новая команда `recommendations:recalc-bought-together` — truncate + заново
  считает пары за 12 месяцев одним `INSERT ... SELECT`, поставлена в
  `Console/Kernel.php` на `->daily()`.
- `coPurchased()` теперь просто читает из кеша (`WHERE goods_item_id = ?
  ORDER BY pair_count DESC`), не считает вживую.

**Осознанное отступление от буквального текста ТЗ** («в оплаченных заказах»):
в реальных данных проекта нет надёжного признака «оплачен» для заказов
наличными — новый `orders.payment_status` (Epic 1) осмыслен только для
карточных заказов (2901 из 2905 заказов стоят на дефолтном `pending`,
включая вообще все заказы наличными), а легаси `orders.paid` всегда `0` и,
похоже, никогда не использовался. Буквальный фильтр «только paid» оставил бы
кеш почти пустым. Взят тот же критерий, что был в исходной живой реализации:
любой неудалённый заказ (`deleted=0`), кроме точно проваленных/отменённых
карточных попыток (`payment_status NOT IN ('failed','cancelled')`).

Живо проверено: команда прогнана на реальных заказах — 10902 пары посчитано.
Товар 9682 (13 совместных заказов с 9683 за 12 месяцев, реальные данные) —
`coPurchased()`/`boughtTogether()` из кеша вернули тот же результат, что и
старый live-JOIN (9683 первым). Реальный HTTP-рендер страницы товара —
HTTP 200, блок на месте.

| Критерий приёмки | Статус |

| Расчёт основан на анализе совместных заказов за последние 12 месяцев | ✅ Проверено |

**Статус: ✅ Готово и живо проверено**

  результат первого шага (4), не пошёл дальше — подтверждает «останавливаемся,
  как только набрали ≥4».
- Категория (`goods_type_id`) — жёстко зафиксирована в каждом вызове
  `similarByStep()`, не ослабляется никогда (структурно, не может быть иначе).

  брендов. Подтверждает «без ограничения по бренду».

**Найден реальный, воспроизводимый недостаток исходных данных** (не блокер
кода, но напрямую связан с открытым вопросом заказчика — раунд 2, №6:

вручную?»): товар 599 имеет заполненное назначение, но все 4 других товара
той же категории — нет. Фильтр по назначению в `similarByStep()` требует
совпадения на **любом** шаге каскада, включая самый ослабленный («только
категория и назначение» — назначение там не снимается, это буквально
последний обязательный сигнал). Из-за этого `similar(599)` возвращает 0,

порядок приоритетов без спроса. Не трогал код; отмечаю как ожидаемое
следствие незаполненности данных, а не баг каскада.

### [BE] Отдача оттенков как вариантов товара

**Статус: ✅ Готово (бэкенд), живо проверено**

Описание: использовать существующую структуру SKU оттенков в 1С для отдачи их на
фронт как вариантов одного товара. Раздельно обрабатывать поля код оттенка
(уникальный идентификатор), номер оттенка, название, цена, остаток, серия — код и
номер не одно и то же поле.

**Решение по объёму (2026-09-04):** не мигрирует существующие товары в
модель «родитель + N вариантов» (риск для SEO, не подтверждён заказчиком) —
аддитивный кеш поверх уже существующих отдельных товаров-оттенков, ничего
не удаляет и не меняет их URL. Новая таблица `product_variants`
(миграция `2026_09_04_120000_create_product_variants_table`), команда
`shades:rebuild-variants` группирует существующие товары по линии
(`goods_item_id.brand_id` — та же иерархия, что уже использует
`ProductRecommendations`/`ShadePalette`), пересчитывается по расписанию
(`->hourly()`, чаще, чем co-purchase кеш — цена/остаток ближе к покупателю).
1С по-прежнему шлёт каждый оттенок отдельной строкой обмена (раунд 2,
блокер №1, без ответа) — трансформер нужен именно поэтому, группировка
целиком на нашей стороне.

**«Код» vs «номер»** — рабочая интерпретация (ТЗ сами термины не разводит):
код = `articol` из 1С (уникальный, например «DLS 9/76»), номер = тон,
разобранный из названия (например «9/76», может повторяться между линиями).
Проверено на реальных данных: номер `9/76` встречается в 5 разных линиях
(id 790/962/2073/862/2676), у каждого свой уникальный код.

_(перепроверено 2026-09-11: `product_variants` — 1030 строк, роут
`GET /ajaxProductVariants` зарегистрирован; те же 1030, что и в сегодняшнем
логе деплоя на dev — согласуется, не регрессия)_

Endpoint: `GET /ajaxProductVariants?goods_item_id=`. Живо проверено: реальная
линия (Estel De Luxe Silver, brand_id=52) — 71 вариант, совпадает с ранее
проверенной палитрой; не-краска — `status:true`, пустой список, без ошибки;
несуществующий товар/без параметра — `status:false`, HTTP 200 везде.

### [BE + FE] CMS: массовый импорт «Назначение» через CSV

**Статус: ✅ Готово и живо проверено (2026-09-09)**
_(перепроверено 2026-09-11: `public/examples/purpose-import-example.csv` на
месте; сам роут — динамический через `RoleManager::routeResponder`
(`/back/{module}/{submenu}/{action}`), не показывается отдельной строкой в
`route:list`, это ожидаемо для этой CMS-архитектуры)_

Ответ на вопрос заказчика 3.4 (part1, 07.09.2026): «можно как-то через
импорт файла заполнить [«Назначение»]?» — импорта товаров в CMS не было
вообще (только экспорт, `GoodsController::exportExcel()`). Реализовано:
новый раздел CMS `/back/goods/goods-purpose-import` (подраздел «Товары»,
`modules_id` id=44, права наследуются от родителя — см.
`database/sql/2026-09-09-goods-purpose-import-module.sql`).

`config('custom.front.purpose_parametr_id')=5` («Beneficii»/«Решение») —
чекбоксы с фиксированным списком из ~35 значений, второй по важности
признак после категории в подборе похожих товаров (п.4 ТЗ). Формат CSV:
артикул + назначение (несколько значений через запятую/точку с запятой,
разделитель самого CSV — `;` или `,`, автоопределяется). Матчинг —
по артикулу (тот же ключ, что везде в проекте). Значения сверяются со
СУЩЕСТВУЮЩИМ списком — новые варианты из файла не создаются самовольно,
незнакомое значение попадает в отчёт. Набор назначения у товара заменяется
целиком тем, что в строке (не дополняется). Пример файла — скачивается
прямо со страницы формы (`public/examples/purpose-import-example.csv`).

Живой прогон через реальный HTTP + admin-логин, реальные товары:

| Несуществующий артикул | ✅ `unmatched_product` |
| Существующий товар + выдуманное значение | ✅ `unmatched_value`, товар не тронут |
| Строка-заголовок CSV | ✅ Корректно пропускается, не попадает в отчёт как «товар не найден» |
